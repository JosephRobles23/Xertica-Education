Migración a Google Cloud Platform

Desacople, esfuerzo de refactorización, arquitectura objetivo GCP-nativa y presupuesto a 1 mes para el piloto de 30 usuarios.

Estado: análisis (no ADR, no código) Fecha: 2026-08-10 Región: us-central1 Cloud Run: scale-to-zero (min=0)

01 Resumen ejecutivo

Veredicto: la migración es factible sin reescritura. La arquitectura ya está pensada para Cloud Run + una base Postgres gestionada, y casi todos los servicios externos viven detrás de un puerto (interface.py/base.py) con mock.py, lo que hace intercambiable la implementación. Es mayormente contenerización + re-plataformado GCP-nativo, no un rediseño.

03 Inventario de servicios y grado de desacople

El backend sigue el patrón puertos/adaptadores: interface.py/base.py (puerto) + service.py + mock.py, con factories en config/dependencies.py que auto-seleccionan mock ↔ real detectando la cadena placeholder. Ese patrón es lo que hace la migración barata donde se respeta. Conviven dos patrones:

  • A) Factory limpio (fácil de intercambiar): get_embedder(), get_linker(), get_storage_adapter(), get_documentation_client(), get_route_structurer(), get_kb_chunk_repository().
  • B) Instanciación directa / cableada (difícil de intercambiar): SupabaseJobRepository(), SupabaseLearningPathRepository(), VideoService(), InfographicService() y tres OpenRouterLLMAdapter() (dependencies.py:27,30,35,53,57-59).

Observaciones de ejecución (relevantes para el refactor)

  • No hay cola ni worker. Los jobs corren en el mismo proceso: asyncio.create_task (video), BackgroundTasks (structure/KB/research). Quiz/lesson/lab/infografía y parseo son 100% síncronos dentro del request HTTP.
  • Estado de jobs en memoria (video/service.py:74-76: _fallback_jobs, _render_tasks) → no sobrevive reinicios ni escala horizontal.
  • Render pesado: subprocess de Remotion (Node + Chrome headless) con timeout de 20 min, más Playwright/Chromium y ffmpeg/ffprobe. Escribe en /tmp/render_{job_id} y composer/public/{job_id} (disco local efímero).
  • Cliente Supabase síncrono dentro de async def sin to_thread → bloquea el event loop.
  • URLs hardcodeadas http://localhost:8000/static/... (infographic/service.py:513-514, adapters/storage/supabase.py:54).
  • Sin autenticación; CORS allow_origins=["*"]. No existen Dockerfiles → contenerizar es trabajo nuevo.

04 Esfuerzo de refactorización

Clasificación S bajo/mecánico · M medio · L alto/estructural.

4.1 Capa de datos: Supabase → Cloud SQL (PostgreSQL + pgvector) M–L

Por qué no es trivial: los repos están escritos contra el query-builder de supabase-py (PostgREST) — .table().select().eq().in_().execute() y .rpc(...) — no contra SQL estándar. No basta cambiar el connection string.

  • (Recomendada) Reescribir los repos con SQLAlchemy/asyncpg. Todo el acceso está aislado tras interfaces, así que se sustituye la implementación sin tocar services. La lógica pgvector está contenida en un punto (RPC match_kb_chunks), que pasa a una consulta SQL con el operador <=> de pgvector.
  • (Alternativa) Correr PostgREST como contenedor apuntando a Cloud SQL — evita reescribir pero añade un componente y no elimina el acoplamiento. No recomendada.

Atender: recrear el schema en Cloud SQL, instalar la extensión vector, portar match_kb_chunks, y decidir qué hacer con RLS (hoy activo sin políticas, key service_role): al mover auth fuera de Supabase, la autorización debe resolverse en la app o en IAM. Retirar los fallbacks in-memory para producción.

4.2 Jobs + worker de render separado L · el foco más caro

Es el cambio estructural principal. Hoy el render es un asyncio.create_task con estado en memoria; para escalar y sobrevivir reinicios hay que:

  1. Externalizar el estado de jobs a Cloud SQL (tabla jobs), eliminando _fallback_jobs/_render_tasks como fuente de verdad.
  2. Encolar el render en Cloud Tasks (o Pub/Sub) en vez de create_task.
  3. Extraer el pipeline de video/executor.py a un contenedor worker como Cloud Run Job, con imagen que incluye Node+Remotion, Chromium y ffmpeg. Toma el job, renderiza, sube el MP4 a GCS y marca el job en Cloud SQL.
  4. Sustituir disco local por rutas efímeras + subida a GCS; eliminar las URLs localhost:8000 y servir assets vía URL firmada de GCS.
  5. Envolver las llamadas síncronas en to_thread o migrar a driver async para no bloquear el event loop.

4.3 Infografía y Google Drive: crear puerto M

  • Infografía (services/infographic/service.py) llama gpt-image-2 con httpx crudo y usa create_client de Supabase dentro del service. Migrar a Vertex Imagen / Gemini image implica crear un puerto y sacar la persistencia hacia el storage adapter.
  • Google Drive (routers/google_drive.py) tiene la integración con httpx dentro del router. Aislar en un adapter y mover OAuth a Secret Manager. Sigue siendo API de Google, no cambia de proveedor.

4.4 LLMs de texto: OpenRouter → Vertex AI nativo M

El puerto ya existe (adapters/llm/base.py). Se crea un VertexLLMAdapter (Gemini directo; Claude vía Model Garden) y se centraliza en un get_llm_adapter(role), reemplazando los OpenRouterLLMAdapter() dispersos. El mapa rol→modelo ya está en settings.model_names.

4.5 Embeddings, Veo/Imagen/TTS, Storage S–M

  • Embeddings (ya factory): nuevo VertexEmbedder tras BaseEmbedder. S
  • Veo/Imagen/TTS ya son Vertex/GCP; falta formalizar el puerto y moverlos a DI en vez de instanciarlos dentro de VideoService (video/service.py:68-71). M
  • Storage: consolidar los dos adaptadores duplicados y crear GcsStorageAdapter tras el puerto. M

4.6 Contenerización + secretos + IaC S–M

Crear Dockerfiles (no existen): imagen de API (Python uv + ffmpeg + Chromium + Node/Remotion para el worker), imagen Web (Next.js standalone). Mover .env a Secret Manager. Añadir CI/CD con Cloud Build + Artifact Registry. Restringir CORS y añadir autenticación.

8.4 Cloud Run — API, Web y Worker

gcloud · build + deploy
# Imágenes (Cloud Build)
gcloud builds submit apps/api --tag us-central1-docker.pkg.dev/PROJECT_ID/xertica/api
gcloud builds submit apps/web --tag us-central1-docker.pkg.dev/PROJECT_ID/xertica/web
# Imagen del worker: base con Node+Remotion, Chromium y ffmpeg + el pipeline de video/executor.py

# API (scale-to-zero para ahorrar; conector de Cloud SQL; secretos)
gcloud run deploy xertica-api \
  --image us-central1-docker.pkg.dev/PROJECT_ID/xertica/api \
  --region us-central1 --service-account $SA \
  --min-instances=0 --cpu=2 --memory=2Gi --concurrency=40 \
  --add-cloudsql-instances=PROJECT_ID:us-central1:xertica-pg \
  --set-secrets=DATABASE_URL=db-url:latest \
  --set-env-vars=GOOGLE_CLOUD_PROJECT=PROJECT_ID,GOOGLE_CLOUD_LOCATION=us-central1,STORAGE_BUCKET=xertica-education-assets

# Web (scale-to-zero)
gcloud run deploy xertica-web \
  --image us-central1-docker.pkg.dev/PROJECT_ID/xertica/web \
  --region us-central1 --min-instances=0 --cpu=1 --memory=512Mi \
  --set-env-vars=NEXT_PUBLIC_API_URL=https://xertica-api-....run.app

# Worker de render (Cloud Run Job: CPU alta, timeout largo, sin concurrencia)
gcloud run jobs create xertica-render \
  --image us-central1-docker.pkg.dev/PROJECT_ID/xertica/render \
  --region us-central1 --service-account $SA \
  --cpu=4 --memory=8Gi --task-timeout=1800s --max-retries=1 \
  --add-cloudsql-instances=PROJECT_ID:us-central1:xertica-pg \
  --set-secrets=DATABASE_URL=db-url:latest
⚠ Sobre min-instances=0 (scale-to-zero)
Ahorra costo — la API solo factura durante requests, mayormente dentro del free tier — a cambio de cold starts (unos segundos en la primera petición tras inactividad) y de no poder sostener trabajo en memoria: cualquier job in-process muere si la instancia se apaga. Por eso min=0 es plenamente seguro una vez externalizado el estado de jobs a Cloud SQL (§4.2). Los endpoints síncronos no se ven afectados salvo por el cold start.

10 Optimización de costos de datos

Cloud SQL es la línea de infraestructura más cara (~$75 de ~$100). A diferencia de Cloud Run, no escala a cero: pagas la instancia encendida las ~730 h del mes aunque esté ociosa >95% del tiempo. A esta escala (30 usuarios / ~5 activos-día) la base de datos nunca es el cuello de botella —lo es Veo—, así que right-sizing baja el costo sin impacto real en performance.

◆ ¿Para qué sirve Cloud SQL aquí?
Hace doble trabajo: (1) el store relacional de los repos del factory (kb, sourcing, documents, source_links, approved), jobs y learning_path; y (2) la búsqueda vectorial del RAG vía la extensión pgvector (match_kb_chunks). Sustituye a Supabase Postgres+pgvector 1:1.

Por qué es caro (y por qué se puede bajar sin perder performance)

El modelo de cobro es la clave: Cloud Run cobra por request y a 0 instancias cuesta $0; Cloud SQL es una VM encendida 24/7 — pagas vCPU + RAM por estar prendida, no por consultas. El ~$75 asume una instancia dedicada (1 vCPU / 3.75–8 GB) que para 30 usuarios está sobredimensionada: estás pagando capacidad que no se usa.
